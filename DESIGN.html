Gather Decisions

Structured input surfaces inside the Claude conversation — an advanced ask_user_input. The agent infers everything it can, renders a form already prefilled with provenance on every value, and the user audits a proposal instead of authoring one.

This document is the input to implementation. Where a decision is marked decided, don't re-litigate it without a reason. One question remains parked until a write path exists. The mockups below are illustrative sketches — click around in them; they behave.

§1

The idea

An MCP App that renders structured input surfaces inside the Claude conversation — forms, matrices, review ledgers — instead of the agent asking six clarifying questions as prose bullets. It is a generic renderer driven entirely by a schema the agent emits at call time. It is not a Salesforce tool, not a planning tool, not a survey product. Those are schemas, not features.

The core inversion. A blank intake form throws away everything chat is good at. The agent should infer as much as it can, then render a form already prefilled, with provenance visible on every inferred value. Reviewing is cheap; authoring is expensive.

Why in-conversation rather than a web app:

  • Context preservation — the form lives in the thread that produced it.
  • The agent generates the schema, so the form is bespoke to the moment.
  • Answers flow back into model context, so the next turn is informed without the user re-narrating what they just clicked.

That last point is the whole thesis. A standalone form collects data. This closes a loop.

§2

Non-goals

  • Not a form designer. No end-user schema authoring UI. The agent writes schemas.
  • Not general-purpose expressiveness. Five opinionated archetypes beat an engine that can render anything mediocrely.
  • No freeform-first forms. If the primary input is prose, it should have been a conversation. Freeform is allowed only anchored to a specific item (per-row correction, per-item note).
  • No gating. Partial submit is a first-class path (§5). A form that requires completion is worse than chat.
  • No domain credentials, no domain writes in v1 (§3).
  • Mobile is view-only in practice for dense views. Don't design for phone editing of a matrix.
§3

Architecture

The server computes nothing about the domain and holds no credentials. It stores form state — schema plus answers — in one Durable Object per form, addressed by unguessable form id, and nothing else.

Decided decided

  • Deploys: Workers Builds git integration — connect the GitHub repo to the Worker for push-to-deploy and PR preview URLs. Not Cloudflare Pages: Pages can't define Durable Object classes, and Cloudflare steers new projects to Workers.
  • Host: Cloudflare Workers, wrangler.jsonc. Streamable HTTP transport (HTTP+SSE is deprecated); the bundle served via Workers Static Assets, not Workers Sites — Sites is the deprecated KV-based path, the same outdated-KV trap as the storage layer.
  • MCP handler: createMcpHandler + MCP SDK v2. decided 2026-08-26 · verified against CF docs The Agents SDK's McpAgent is deprecated and feature-frozen (it put every MCP session in its own DO); the current recommendation is the stateless createMcpHandler from the agents package with @modelcontextprotocol/server v2 — one server instance per request, no session state, cross-request data "behind an authenticated handle in a Durable Object", which is exactly the per-form DO. Caveat accepted: server-pushed elicitation/sampling don't work on this path; client-initiated tools/call and resources/read — all this app uses — are unaffected.
  • Server-minted form ids. decided 2026-08-26 The Worker mints formId (crypto-random) and returns it in the stub tool result — which is also how the agent learns the id to pass to load_form and to chain forms. Agent-authored ids ("fls-review") would be low-entropy and guessable, which is fatal when the id is the only capability.
  • Document mode. decided 2026-08-26 Forms are re-openable documents, not one-shot events: one Durable Object per form, addressed with idFromName(formId); load_form(id) re-renders with accumulated state. The id is the capability, so no auth is reintroduced. DO over KV because the pattern is per-entity and write-heavy: draft writes and the agent's reads arrive through different routes, and KV's eventual consistency (last-write-wins, up to ~60s propagation) could prefill a chained form from a stale draft. A DO routes every request for the id to one instance — strongly consistent, serialized writes. SQLite stores answers as rows (autosave updates changed paths, not the whole blob); an alarm makes the form self-expiring after 30 days idle (clock resets on any read or write) — with compatibility date ≥ 2026-02-24, the expiry handler is a single deleteAll() (it clears the alarm too), and since DO storage is billed as of Jan 2026 the TTL has real cost benefit; WebSockets are there if live multi-device sync is ever wanted.
  • Autosave transport: an app-visible tool, never a direct request. decided 2026-08-26 The iframe cannot POST anywhere — that's the point of the CSP below. Drafts reach the server through a visibility: ["app"] tool (save_draft) called over the host bridge; the host mediates, the CSP stays default-src 'none', and "the app cannot phone home" survives intact. Hardening: the DO caps answer-payload size and throttles per-form write rate, so a leaked id can't be spammed.
  • No auth. No domain credentials; form state at rest is reachable only via its unguessable id. Custom connectors are reached from Anthropic's cloud, so the endpoint is public regardless — hardening is an unguessable base path, no IP allowlist (§10).
  • No CSP domains declared. corrected 2026-08-26 · verified vs spec ui.csp omitted, so the host's restrictive default applies: default-src 'none'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; media-src 'self' data:; connect-src 'none'. The conclusion holds — connect-src 'none' means the app physically cannot phone home — and inline scripts/styles and data: images are allowed, which the single-file bundle relies on. (The draft's stated value, bare default-src 'none', would have blocked the bundle's own inline JS.) CSP is declared via structured fields (connectDomains, resourceDomains, …), not a raw string; hosts may tighten, never loosen. Self-contained bundle: no CDN, no external fonts.
  • No logging of payloads. Document mode means answers do rest in the form's Durable Object, so the privacy story is stated honestly: stored only under the unguessable id, never logged, self-expiring via alarm. Weaker than "never touch the server" — accepted as the cost of re-openable forms.
  • The schema arrives as tool input, not as a tool result. The tool result is a short stub ("Form displayed; awaiting input.") because result text lands in model context and must not echo the schema back into it.
  • Build a real bundle. Claude's iframe sandbox blocks HTTP script sources, so a Vite dev server won't load. Serve a prebuilt production bundle; send notifications/resources/list_changed on change so the host re-fetches.
Consequence of document mode

Autosave falls out for free — debounced writes to the form's DO kill the half-filled-form data-loss risk, and ui/resource-teardown becomes a final flush rather than the only one. The costs: a store to operate, and the weaker privacy story above.

§4

The meta-schema

4.1 Closed vs free — the sorting rule decided

The single most useful constraint in the whole design:

ContentsValidated
Closed vocabulariesfield types, render hints, answer states, rule ops, rule actions, source valuesYes, strictly. The renderer switches on these.
Free textlabels, titles, descriptions, option display text, rationale, notes, placeholdersNo, beyond length limits

The agent gets total latitude over what the form says. The renderer only ever branches on things it can actually understand. If the renderer or a computed counter must act on it, it's typed. If a human reads it, it's free.

Corollary: the agent decides button labels and their values ("Confirm / Fix / Later", "Yep / Nope / TBD") — defer options are ordinary agent-defined options, not a fixed state (§4.3).

4.3 Answer shape decided

Flat map, path-keyed, uniform across values and notes:

type AnswerState = "answered" | "empty";

type Answer = {
  state: AnswerState;
  value?: unknown;      // absent when empty
  note?: string;        // free text, anchored to this path
};

type Answers = Record<Path, Answer>;

Defer is not a special state. decided 2026-08-26 "You decide", "Let's talk" and "TBD" are ordinary agent-defined options: a field with four options accepts five states — each option plus empty — and that's it. The agent authors the label/value pairs at creation time and is the party that interprets them on the return trip; the renderer never assigns meaning to them. There is no blocking boolean — the agent knows what its own lets_talk value demands downstream because it authored it, and the recipes (§6.2) carry the conventions.

Two mechanics preserve what a special state would have provided:

  • skipOptions on any field. Non-select fields (date, number, matrix cell) may declare agent-defined label/value pairs rendered as a skip affordance beside the input. "Let Claude decide" in an elicitation form and "TBD" in a ledger are the same mechanism with different agent-authored pairs.
  • computed counts by equality, never meaning. "Count answers where value = lets_talk" is an equality match on an agent-declared identifier — the same thing the renderer already does with field ids, so §4.1 holds.

The open-questions register is therefore not an archetype — it's the agent filtering its own defer values across the session (which persist in the form document, §3).

4.4 Notes

Free-text note on any path. Sparse by design.

  • Rendering: an icon that expands, with a visually distinct filled state. Never forty visible textareas — that makes a form look like homework.
  • Transport: push back as {path, label, note} triples so the agent can open directly on them ("you flagged rollout timing: 'depends on Legal'"), not as an opaque blob it must re-read. The anchor surviving is the entire value over prose.

4.5 Path grammar decided

Closed, parseable, validated against the schema. Not JSONPath — no wildcards, no filters.

path    := segment ( "[" id "]" | "." id )*
segment := id | "$self" | "$parent"

// examples
region
fls[Discount__c][SalesOps]
stakeholders[r_7f3a].owner
$self.detail

Ordinal vs stable id — the rule that prevents silent corruption:

StructureAddressingWhy
matrix rows/colsagent-declared idsfixed for the life of the view
repeatable, table rowsclient-minted ids (r_7f3a)user-mutable; deleting row 2 must not re-point notes anchored at [3]
rankminted idsposition is the value being edited, so it can't also be the address

Ordinals are for display, never for persistence. Nice side effect: this addressing scheme is the sparse-exception format the matrix needs. Dense grids are never serialised.

4.6 Rules — flat list, $self for row scope decided

Nested boolean trees are where model-generated schemas fall apart. Flat list, evaluated in order:

type Rule = {
  when: {
    field: Path;                                    // may use $self
    op: "eq"|"neq"|"in"|"gt"|"lt"|"empty"|"filled";
    value?: unknown;
  };
  then: {
    action: "show"|"hide"|"enable"|"disable"|"require"|"optional"
          | "filter_options"|"set_default"|"clear";
    targets: Path[];
  };
};
Not rendered = empty · decided 2026-08-26

The user submits exactly what they see. The submit payload is a function of the rendered view and nothing else. A hidden field contributes empty no matter what it held before; no cached or invisible state is ever submitted. If a re-shown field restores a prior value, that's fine because the user sees it before submitting.

Corollaries: set_default writes only into empty fields — it never overwrites a value the user entered; and rule evaluation re-runs the flat list after every change until the rendered state is stable (small iteration cap; the validator warns on rules that could cycle).

  • Engine semantics fixed at build step 3 decided 2026-08-26 — set_default is a derived overlay like prefill (never writes the answer store, so a user edit always wins and "writes only into empty" holds by construction, and the overlay disappears when its condition flips); clear is edge-triggered (fires when its condition turns true — never a standing "while true, be empty", which would blank data the user can see); comparison ops (eq/neq/in/gt/lt) are all false on an empty value — only empty/filled test presence; two filter_options on one path intersect; a condition on a container or column holds only if it holds for every leaf beneath it; a stored answer filtered out of its option set is effectively empty; hitting the iteration cap renders the last pass and flags it rather than failing; a show target starts hidden and an enable target starts disabled.
  • require/optional mark, they never gate. Partial submit is always available (§5); required-ness renders as a marker and feeds computed counters and section status. Only malformed values block submit (§6.3).
  • filter_options is half the value and is the one people forget. Pick "AWS" → the region field only offers AWS regions. Without it you get invalid combinations and a form nobody trusts.
  • Rules target fields or sections, so whole sections appear from one answer.
  • $self resolves to the current row inside a repeatable/table. This is what makes per-row conditional follow-up work at all — the agent can't emit one rule per row when the user adds rows at runtime.

4.7 Prefill envelope decided

Every prefilled value carries provenance. This is what makes it a Claude-native form rather than a web form.

type Prefill = {
  value: unknown;
  source: "user" | "inferred" | "default" | "existing";
  confidence?: "high" | "low";
  rationale?: string;      // "you mentioned EU customers"
  needsReview?: boolean;
};
  • Render inferred + low visibly distinct, rationale on hover/expand.
  • Header shows a computed "N inferred values need review" counter — the count_needs_review op: prefills marked needsReview: true that hold no answer yet. Any touch on the field, even confirming the prefilled value, writes an answer and clears it. (count_empty reads 0 on a fully-prefilled form — the audit added this op for exactly that reason.)
  • existing gives baseline-diff behaviour for free — dirty-cell rendering in a matrix, changed-value marks elsewhere.
Never emit a blank form

If there's nothing to prefill, the form probably shouldn't exist.

4.8 Sections

type Section = {
  id: string;
  title: string;
  description?: string;
  fields: Field[];
  layout?: "stack" | "two_col";
  initially?: "expanded" | "collapsed";
};

Persistent left rail in fullscreen, with per-section status: untouched / in progress / complete / has errors. That rail is the single biggest usability difference between this and a long scroll — this document's own left rail is the same idea. Guideline-compatible too: collapsible sidebars, tabs and pagination are the sanctioned disclosure patterns; floating panels are not.

Soft limit ~7 fields per section. Never a section with one field.

§5

Archetypes

decided These are generation recipes, not code paths. One renderer, one meta-schema, N markdown recipes. Adding an archetype costs a file, not a deploy.

5.1 Assumption ledger — build this first

The highest-value surface, and the one that justifies the project. The failure mode it fixes: a plan requires forty small inferences. The user catches two wrong ones on read-through and the other thirty-eight stay wrong silently — not agreed to, just invisible. Nobody audits a paragraph for premises.

Shape: dense list of inferences, each a single_select with render: segmented, plus agent-defined defer options ("You decide" / "TBD"), plus optional per-row note and a conditional correction input. Every row carries source + rationale — and row provenance is not a row property (audited 2026-08-26): each verdict is prefilled confirm with source/confidence/rationale/needsReview, so the provenance chip, the count_needs_review counter and bulk affirm all read the one §4.7 envelope — bulk affirm is "accept the needs-review prefills". With forty rows of identical shape, generate it columns+data (§4.2 table): the segmented options are declared once as a column definition, rows are data.

5.3 Brainstorm convergence

The agent has just produced fifteen options in prose and the user must prune, rank and combine. Options come from the conversation, not a catalog. Audited shape (2026-08-26): candidates are a table with a boolean keep column and a $self-scoped rejection-reason select — not a multi_select, because rule ops have no membership test over multi-valued answers and the per-candidate reason needs row scope anyway — plus repeatable "add your own". Ranking the survivors is the next form in the chain (§5.6): rank items are declared at authoring time, and the survivors aren't known until the prune comes back. allocation for effort split rides in that second form too.

Capture rejection reasons. When twelve options become two, why the other ten died is more informative than the pick — it reveals the shape of the constraint. One-tap reasons: too expensive / too slow / wrong team / already tried / not the problem. Cheap for the user, disproportionately useful for the agent.

5.4 Plan confirmation / draft review

Fully prefilled, diff-shaped, fullscreen. Everything source: "inferred" with rationale, computed totals, explicit commit action. Draft review collapses into this: plan sections are info fields with ids, each with approve/revise + note. "The third bit is off" is unresolvable in prose; a note anchored to section three is not. No separate renderer needed.

5.5 Matrix

The hard field type, and the best single argument for the whole pattern. Awkward in chat (inherently 2D), awkward in the source system (per-field clicking), awkward in a spreadsheet (the spreadsheet doesn't know the rules).

amber dots = dirty vs source: "existing" baseline — the diff is what gets summarised to the model, never the grid
  • No dropdowns in cells — interaction scales with option count. decided 2026-08-26 Two clicks × 800 cells is untenable, and dropdowns clip. Two closed modes, picked by the renderer from the cell's option count, overridable via render hint: cycle (≤4 options — click/space advances, drag-fill paints the current value; the mockup above) and paint (5+ — a value palette in the matrix toolbar: select the value once, click or drag cells to apply, number keys 1–9 pick palette entries). Palette entries reuse the option shape everything else renders — {value, label, description?} — label shown, description on hover, so a 10-value palette carries its own context the way render: cards does. Cycling degrades past ~4 options (a wrong click costs ~n/2 more, and the next value stops being predictable); painting is also the better bulk model at high cardinality. A per-cell popover is a secondary affordance, fullscreen only (§7.3).
  • Header-click bulk apply (column, row) — 90% of real editing. Semantics: a header click sets the whole group to one value — next(first cell's value) in cycle mode, so a uniform group cycles naturally and a mixed group unifies on the first click; in paint mode it applies the palette selection, so no ambiguity exists. Bulk apply is constraint-aware: the option set is uniform by construction (one cellType, §4.2), but per-cell constraints can forbid the target value — those cells are skipped with feedback ("3 cells skipped — constrained"), never silently coerced. A changed-to-empty cell renders visibly dirty, not merely blank.
  • Rectangle fill — shift-click or drag to paint a region.
  • Diff against baseline — source: "existing" renders dirty cells distinctly, with an N-changes counter and per-cell revert.
  • Column collapsing — 30 columns don't fit; group, and offer "hide columns with no exceptions".
  • Keyboard nav — arrows + space. Required for accessibility anyway.
  • Per-cell constraints in the schema, so illegal combinations auto-correct and explain themselves. (Domain example: Edit implies Read; required and master-detail fields can't be hidden; formula fields are read-only.) The renderer enforces; it doesn't know the domain.
  • Never send the grid to the model. content gets a policy summary ("38 fields; default read-only; Edit for Sales Ops and Rev Ops; 4 exceptions"). Dumping 1,000 cells burns thousands of tokens and invites hallucinated cells.
  • Direct DOM mutation on changed cells — per-cell memoized components (§8). No full reconcile per click; hosts impose resource limits on views.

5.6 Cross-archetype mechanics decided

More important than any field type.

  • Partial submit. "Answered three of ten, continue." Unanswered fields are enumerated as empty in the submit payload; the agent decides whether to pick for them or ask. Preserving the chat affordance of "just pick something for the rest" is what keeps this better than software.
  • Always leave the chat escape hatch. A line in the card — "or just tell me" — costs nothing and turns a mistriggered form from a dead end into a minor annoyance.
  • Forms chain. elicitation → draft → convergence → plan → confirmation. Continuity is twofold: ui/update-model-context for what the agent must know, and the form's Durable Object for exact state (§3) — the agent passes formIds forward instead of re-serialising answer maps and minted row ids through its own context. Push back structured state, not a prose summary, or form three can't be prefilled from form one.
§6

Guidance: five layers

The trigger is a conversational moment, not a topic — the user asks for clarification, a brainstorm, or plan confirmation. They will never say "questionnaire". This breaks skill-description matching as the primary trigger, so the layers split by what's in context when.

6.1 Tool description — carries the trigger

Always in context, so it costs tokens every conversation. Keep it minimal but put the trigger logic here, because nothing else is loaded at decision time. Write it behaviourally and negatively — fire on something the model can notice itself doing:

If you are about to write clarifying questions as prose bullets, stop — those go in this tool instead. Same if you are about to list options for the user to pick from, or summarise a plan for approval.

And the don'ts, which matter more, because a needless 18-field form reads as bureaucracy. False positives cost more than false negatives:

  • One question → just ask it.
  • "A or B?" → they want analysis, not their options back as radio buttons.
  • User already gave detailed constraints → don't second-guess with an intake form.
  • Venting, exploring, thinking out loud → a form is a wall.

Name the tool for the behaviour. gather_decisions gets selected at the right moments. render_questionnaire gets selected when someone says "questionnaire", which never happens.

6.2 get_form_guide(archetype) — carries the craft decided

This, not a skill, is the primary guidance channel. A model-visible tool returning the archetype recipe + two worked examples. The render tool says: "If you have not called get_form_guide in this conversation, call it first."

Why it beats a skill pointer: a tool call is far more reliably performed than a file read — it's what the model is already doing. Host-agnostic: no plugin, no install, no Claude-only dependency. Updated by deploying a Worker, not by asking teammates to re-upload a skill. Zero standing token cost. Costs one round trip, which is nothing next to a human filling a form.

6.3 Validator — enforces, and teaches

Two loops, both required.

Schema validation (agent → app). Malformed definitions come back as text in the tool result: unknown field type 'slider_group', rule 3 references missing field 'region', path 'stakeholders[2].owner' uses an ordinal — use a minted row id. The agent self-corrects on the next call. Without this the tool silently renders garbage and you never learn why. Return the matching worked example alongside the errors — that makes convergence work even with no skill and no guide call. Design the inputSchema loose and validate strict in the app: deeply nested recursive JSON Schema degrades model output quality.

Answer validation (user → app). Format only gates. decided 2026-08-26 Malformed values — wrong type, out of range, failed regex — block submit and jump the section rail to the error, because submitting garbage helps nobody. Required-ness never gates: partial submit is the norm (§5.6), require is a marker that feeds the rail, the asterisk and computed counters, and unanswered required fields simply return empty. The agent reads "3 of 4 required fields empty" in the payload and decides what to do — that decision is its business, not the renderer's.

6.4 Skill — carries the whether

Not examples; the server serves those. The skill's job is the thing the server can't see: the §6.1 negative rules about the agent's own output, loaded before any tool is selected. Metadata is ~100 tokens always-loaded; the body loads on trigger.

Package as a plugin (connector + skill + /… command) so a teammate installs one thing. Plugins can pull from a git repo, which matters for a skill iterated weekly; org-level skills must be uploaded and updated manually. Plugins are Claude-specific — the portable equivalent is the MCP prompts primitive. Write the skill after the validator: its error log tells you which mistakes to write guidance against, instead of guessing.

6.5 Memory / CLAUDE.md — carries the user's process decided

How the agent interprets answers is not the server's business. "When I defer, just pick something", "anything marked 'let's talk' means stop and ask", "never render a form for fewer than 3 questions" — these are per-user/per-team process preferences and live in CLAUDE.md or agent memory, not in recipes.

The split: recipes (§6.2) ship user-agnostic defaults so a fresh user with an empty CLAUDE.md gets coherent behaviour; memory/CLAUDE.md overrides them. Repeated form sessions are high-signal preference data — "this user defers all budget questions every time" — and memory is the intended place for that learning to accumulate.

§7

Host integration (MCP Apps)

Extension io.modelcontextprotocol/ui (SEP-1865, Stable 2026-01-26).

7.1 Declaration

// resource
{
  uri: "ui://forms/renderer",
  name: "Structured input renderer",
  mimeType: "text/html;profile=mcp-app",
  _meta: { ui: { prefersBorder: true /* per display mode */ } }
}

// tool
{
  name: "gather_decisions",
  description: "…trigger logic from §6.1…",
  inputSchema: { /* loose */ },
  _meta: { ui: { resourceUri: "ui://forms/renderer", visibility: ["model","app"] } }
}

One UI resource serves every form type forever: rendering engine ships in the bundle, schema arrives as data. Host reviews the template once; new archetypes are server-side only. Use visibility: ["app"] for anything the UI needs but the model shouldn't see (save_draft, validation helpers); visibility defaults to ["model","app"]. App-scope is per-server; hosts MUST reject app calls to tools lacking "app", and cross-server calls from apps are blocked. Verified nuances: the _meta.ui block is served with the resource contents via resources/read; use the nested _meta.ui.resourceUri form — the flat _meta["ui/resourceUri"] key is deprecated. The app calls tools with plain MCP tools/call over a postMessage JSON-RPC transport; the host proxies to the server.

Context discipline: debounced mid-fill pushes carry a summary ("section 2 of 5 complete; 3 inferred values unreviewed"), not the payload. Full structured answers only on submit. ui/update-model-context overwrites each time and does not trigger a turn — exactly the semantics wanted.

7.3 Display modes and constraints

The spec defines three modes — inline, fullscreen, pip. This app uses the first two.

Inline card — progress/summary surface and small elicitation forms. Auto-fit height, no nested vertical scroll, ~2 actions at the bottom, 4–5 data points, no drill-ins, no menus or popovers (clipped by the host container, z-index conflicts).

Fullscreen — everything dense. Composer stays visible. No floating panels; use the section rail, tabs or pagination. The app supplies its own fullscreen button; the host supplies close. Menus in fullscreen: the hard prohibition is scoped to inline cards; in fullscreen it's a preference. Your view is the viewport, so host clipping mostly disappears — but your own overflow: auto still clips, and there's no portaling out of the sandbox. Use the Popover API / CSS anchor positioning / top-layer <dialog>, which escape ancestor overflow within your document. Keep menus to genuinely secondary actions; never the core loop.

Mobile — native WebView, not an iframe. No camera/mic/geolocation. Connectors must be added on web or desktop first. Critically: vertical pan gestures inside an inline app go to the conversation scroll, so inline apps must fit their content height; request fullscreen if you need your own scroll viewport. 44pt tap targets, honour hostContext.safeAreaInsets (not mobile-only — the composer can overlay the bottom of an inline app on web too). Dense matrix on a phone: render a per-field summary list instead. Editing is a desktop/tablet affordance.

7.4 Theming

Host supplies CSS custom properties via hostContext.styles.variables (standardized --color-*, --font-*, --border-radius-*, --shadow-* keys) — plus theme, locale, timeZone, containerDimensions, safeAreaInsets, platform, deviceCapabilities, displayMode / availableDisplayModes, toolInfo, and styles.css.fonts (host-injected @font-face CSS).

Never hardcode colors. Structural elements (backgrounds, text, borders, icons) use host tokens; brand colors only for accents. Set your own :root fallbacks for every variable used, since hosts may supply a partial set. Support light and dark; test both. Skeleton loaders, not spinners.

7.5 Claude-specific constraints verified 2026-08-26

  • Rendering requires a per-app user permission prompt ("Always allow") on first use.
  • App-initiated tools/call is proxied through Claude's backend (egress from Anthropic IP ranges) — consistent with §3's threat model.
  • Tool results over ~150k characters get spilled to the code-execution sandbox as a file pointer — never applicable here (stub results and save_draft acks are tiny), but a reason to keep it that way.
  • ui/open-link shows a confirmation modal; frameDomains (nested third-party iframes) is restricted in Claude — both unused by this app.
  • _meta.ui.domain (stable sandbox origin for in-app OAuth) exists but is irrelevant — no auth (§3).

Draft-spec watchlist (in ext-apps draft, not yet in a dated release): app-provided tools the agent can call (a pull-based complement to ui/update-model-context — could let the agent query form state instead of being pushed summaries), ui/download-file (host-mediated downloads — a future "export answers as CSV"), and sampling/createMessage from apps. Revisit when the extension cuts its next release.

§8

Stack decided 2026-08-26

React, bundled by Vite into the single ui:// HTML resource. React libraries are allowed, with one hard constraint: nothing may fetch at runtime.

Why React over vanilla: the renderer is a schema-driven component tree with conditional visibility, per-row rules, computed counters and re-evaluation on every change — exactly the shape React exists for. Vanilla JS here means hand-rolling a worse reconciler. The framework is invisible to the host either way: everything is compiled into one self-contained bundle, so the choice costs nothing at the MCP boundary.

Why the constraint is absolute: _meta.ui.csp is omitted (§3), so the iframe runs under default-src 'none'; connect-src 'none'. A library that loads CSS from a CDN, pulls a font, or phones telemetry home doesn't degrade — it breaks silently. Everything must survive being inlined at build time.

  • Prefer headless libraries: TanStack Virtual if matrices outgrow naive rendering; dnd-kit (rank, drag-fill); Radix primitives (portals stay in-document, which is fine inside the iframe; top-layer <dialog>/Popover API for fullscreen menus per §7.3); Zod shared between Worker and client so the validator is one codebase (§6.3). TanStack Table was dropped at build step 3: the schema already is the column model and the per-path store is the value model — a second row/column state would fight the per-cell memoization §5.5 depends on.
  • Skip TanStack Form — not disallowed, redundant. The path-keyed answer map, minted ids, rules engine and computed evaluation are the form-state library, and they're build step 1 either way; a second field-state store means two sources of truth.
  • shadcn/ui — yes. It's vendored source, not a dependency: components are copied into the repo (on Radix), so nothing can phone home and anything can be stripped. Its theming is entirely CSS-custom-property-driven, so its tokens (--background, --primary, …) are pointed at hostContext.styles.variables with :root fallbacks — §7.4 satisfied by the component system. Tailwind is fine because it's build-time static CSS, not a runtime; no external @imports or fonts in its config. Inline cards still get no menus (§7.3 — a host rule, not a library one).
  • Avoid styled component kits (MUI, AntD): bundle weight, font fetching, and they fight §7.4 — host tokens must own all structural color, and a themed kit wants to own it instead.
  • Matrix performance: the §5.5 "direct DOM mutation" requirement is satisfied with per-cell memoized components — a click re-renders one cell, not 800. If bundle size ever becomes a problem, Preact + preact/compat is a near-drop-in ~40KB saving; decide at build step 3, not now.
  • Styling: shadcn's Tailwind output plus plain CSS where clearer, all over host custom properties with :root fallbacks. No CSS-in-JS runtime.

8.1 Toolchain decided 2026-08-26

  • Monorepo, pnpm workspaces: packages/schema (types + Zod validator + path parser — imported by both Worker and UI, which is what makes §6.3's validator one codebase), packages/ui (renderer bundle), packages/worker (MCP handler + form DO).
  • Zustand for the answer store. A vanilla store with per-path selectors gives per-cell subscription granularity — the mechanism behind §5.5's "a click re-renders one cell, not 800" — and the rules engine runs against the same store outside React.
  • Vitest throughout; @cloudflare/vitest-pool-workers for DO/handler tests. Biome for lint + format. TypeScript strict.

8.2 Visual language decided 2026-08-26

Aesthetics are mostly not ours to decide — §7.4 means the form inherits Claude's theme and should read as part of the conversation, not an embedded website. What the app owns, normatively defined by the mockups in this document:

  • Provenance chips are the one semantic color system: amber = inferred, blue = user-said, neutral = existing. Nothing else gets semantic color.
  • Segmented controls are the default answer affordance; counters are pills; the note icon has a distinct filled state.
  • Density per the §5 mockups — a ledger is a dense audit surface, not a spacious marketing form.
  • Accent once per surface (the primary action), skeletons never spinners (§7.4), motion minimal.

Five things the real APIs made different from the sketch above, all verified against live docs:
    • Durable Object classes are declared with the new exports block ({ type: "durable-object", storage: "sqlite" }). The Wrangler config reference now calls the imperative migrations array with new_sqlite_classes "the legacy imperative configuration" and steers new Workers to the declarative field; the two are mutually exclusive. Same backend, same guarantees.
    • nodejs_compat is required: agents/mcp/server imports node:async_hooks.
    • notifications/resources/list_changed cannot be pushed from a stateless handler — there is no connection to push down, and notify.resourcesChanged() reaches only clients holding a subscriptions/listen stream. So a host that cached the bundle keeps it until it re-reads. Recorded, not worked around: the alternative was an unauthenticated trigger endpoint on a server with no auth.
    • get_form_state is a fifth tool the draft did not have, and it is forced by §7.2: the host delivers only tool input to the app, so a load_form render arrives knowing nothing but the formId and has to pull its own schema and answers.

Still to do: deploy, and connect as a custom connector.

Remaining archetypes, in order of use: elicitation → confirmation → convergence → matrix. done 2026-08-26 (332 tests: schema 132, ui 150, worker 50; single-file bundle 445 KiB / 130 KiB gzip, verified self-contained.) Every §4.2 field type now has a control, the matrix included; the bridge↔worker wiring the Worker's own report asked for; and a sixth fixture, convergenceRank — the §5.3/§5.6 chained second form — which now ships as convergence's second worked example, because "ranking is the next form" is easier to show than to say. Six things this step decided or found:
    • Inline is two surfaces, and the form picks which. A SMALL form now renders for real inline — the §5.2 elicitation card, fields and all — because a card that only says "open me" replaces nothing, and replacing three turns of Q&A is the entire point of that archetype. The summary card stays for anything dense: more than eight answerable fields, or any table/matrix, none of which can fit their own height inside a conversation scroll.
    • allocation: the set constraint gates in one direction only. Over-allocating is malformed and blocks submit — the agent's own total says that split cannot exist. Under-allocating submits, and the remainder rides in the payload, because partial submit is the norm and "3 of 100 allocated" is information, not an error. The answer is one path PER MEMBER, which is what the leaf enumeration already said an allocation is, and what lets sum add it and a note anchor into it.
    • Two matrix mechanics the spec left open. Cycling never walks through empty — a sequence of n+1 stops is not the "≤4 options" §5.5 describes — so Delete clears the focused cell, and that is how a changed-to-empty dirty cell arises. And shift-click PAINTS the anchor's value across the rectangle rather than advancing the cell you finished on, so the region depends on what you were spreading, not on where you stopped. Also: allowed restricts the cycle SEQUENCE as well as the paintable set, so a formula-field row cycles within its legal values instead of proposing an illegal one and then skipping every cell.
    • One engine gap, now closed: reset(path) deletes the entry. Per-cell revert is inexpressible without it — empty is a decision the user made and submits as one, so a cell reverted with setEmpty would read as dirty against its baseline forever. Untouched and empty are different states and §4.7 needs both.
    • The searchable list is where §7.3 bites hardest. Fullscreen gets a top-layer modal <dialog> — the only escape from ancestor overflow available, since there is no portaling out of the sandbox. Inline gets the same list IN FLOW, and the card grows; the prohibition on popovers in an inline card is a host rule, so degrading is the only honest answer. (Tailwind's preflight zeroes the margin a top-layer dialog needs for its own centring — put it back.)
    • DEFERRED, deliberately: matrix column collapsing, and a mobile EDITING surface for the grid. On platform: "mobile" the matrix renders as a read-only per-field value list per §7.3 ("editing is a desktop/tablet affordance"), not as nothing. multi_select matrix cells get the per-cell top-layer popover §5.5 allows as a secondary affordance, since a set has no next() to cycle to.
    One performance note worth keeping, because it is the §5.5 requirement in miniature: everything transient in the matrix is kept OUT of React state — the palette selection and the drag anchor live in a mutable controller the memoized cells hold a stable reference to, and the focus cell is real DOM focus moved with .focus(). A selector that MINTS its result instead (an {path, text} object) re-renders on every store notification and then loops; that bug was caught by the new tests and is why every hook in state.tsx returns a primitive or a reference-stable value.
  6. Skill + plugin packaging, last, informed by the validator's error log.
§10

Resolved questions

Composite table cells decided · allowed

With the columns+data pattern the options live once in the column definition, so a multi_select column is cheap. Costs one extra path level in the answer map — accepted.

Form as event or document decided · document

Forms are re-openable and re-renderable with accumulated state — the session's shared artifact. Stable formIds and one Durable Object per form follow (§3). Draft persistence is subsumed: the DO addressed by an unguessable id is in from the start; the id is the capability, so no auth is reintroduced.

Endpoint exposure decided · unguessable path only

No IP allowlist — Anthropic's egress ranges are shared infrastructure, so allowlisting never isolated to one org and adds maintenance for little benefit.

Audit attribution parked

With no domain-write path nothing needs attribution. Revisit the moment one is added.

Deferred label taxonomy dissolved

No blocking boolean, no special deferred state: defer options are ordinary agent-defined label/value pairs the agent interprets itself (§4.3).
